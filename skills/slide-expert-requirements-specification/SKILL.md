# Requirements Specification Expert

A specialized skill for creating comprehensive requirements documentation and presentation slides that align stakeholders and clearly define functional requirements, non-functional requirements, constraints, and assumptions.

## Core Purpose

This skill transforms complex requirement information into clear, structured presentations that enable stakeholder alignment and project success. It bridges the gap between technical specifications and business needs.

## When to Use This Skill

Activate this skill when you need to:
- Create requirements specification slides for stakeholder review
- Document functional and non-functional requirements
- Prepare for project kickoff or requirement review meetings
- Align technical and business stakeholders on project scope
- Create system specification documentation
- Present business requirements in a structured format
- Document constraints, assumptions, and project dependencies

## Requirements Organization Framework

### Business Requirements Layer
- **Goals and Objectives**: High-level business outcomes
- **Success Metrics**: How success will be measured
- **Stakeholder Needs**: What different stakeholders require
- **Business Value**: ROI and business impact justification

### Functional Requirements Layer
- **System Behaviors**: What the system must do
- **User Stories**: Who needs what functionality and why
- **Use Cases**: Detailed interaction scenarios
- **Data Requirements**: Information structure and flow
- **Integration Points**: External system connections

### Non-Functional Requirements Layer
- **Performance**: Speed, capacity, and response times
- **Security**: Authentication, authorization, and data protection
- **Usability**: Ease of use and accessibility
- **Reliability**: Availability and error handling
- **Scalability**: Growth and capacity planning

### Constraints and Assumptions Layer
- **Technical Constraints**: Platform and technology limitations
- **Business Constraints**: Budget, timeline, and resource limits
- **Regulatory Constraints**: Compliance requirements
- **Assumptions**: Project dependencies and preconditions
- **Risks**: Potential issues and mitigation strategies

## Slide Structure Template

### Phase 1: Context Setting (Slides 1-3)
1. **Cover Slide**: Project title, version, date, audience
2. **Executive Summary**: Business problem, solution overview, key outcomes
3. **Project Background**: Current state, business opportunity, success criteria

### Phase 2: Scope and Stakeholders (Slides 4-5)
4. **Scope Definition**: In-scope/out-of-scope, boundaries, exclusions
5. **Stakeholder Analysis**: Key stakeholders, roles, responsibilities, interests

### Phase 3: Requirements Overview (Slides 6-7)
6. **Requirements Categories**: Business, functional, non-functional overview
7. **Priority Matrix**: Must-have/should-have/could-have with rationale

### Phase 4: Detailed Requirements (Slides 8-10)
8. **Functional Requirements**: User stories, use cases, system behaviors
9. **Non-Functional Requirements**: Performance, security, usability criteria
10. **Data and Integration**: Information architecture, system interfaces

### Phase 5: Constraints and Planning (Slides 11-13)
11. **Constraints and Assumptions**: Technical, business, regulatory limitations
12. **Risk Assessment**: Key risks, impact analysis, mitigation strategies
13. **Implementation Roadmap**: Phases, milestones, dependencies, timeline

### Phase 6: Validation and Next Steps (Slides 14-15)
14. **Acceptance Criteria**: How success will be validated and measured
15. **Next Steps**: Approval process, immediate actions, responsibilities

## Documentation Best Practices

### Writing Principles
- **Clarity Over Jargon**: Use plain language that all stakeholders understand
- **Measurable Criteria**: Every requirement should be testable and verifiable
- **Visual Communication**: Use diagrams, flowcharts, and tables to enhance understanding
- **Traceability**: Link business goals to technical requirements
- **Consistency**: Use standardized terminology and formats throughout

### Quality Standards
- **Complete**: All necessary requirements are documented
- **Correct**: Requirements accurately reflect stakeholder needs
- **Feasible**: Requirements can be implemented within constraints
- **Necessary**: Each requirement serves a specific purpose
- **Unambiguous**: Requirements have a single, clear interpretation

## Content Creation Guidelines

### Functional Requirements
Use this format for each functional requirement:
```
**FR-[ID]: [Brief Title]**
- **Description**: What the system must do
- **User Story**: As a [user type], I want [functionality] so that [benefit]
- **Acceptance Criteria**: Specific, testable conditions
- **Priority**: Must-have/Should-have/Could-have
- **Dependencies**: Related requirements or external factors
```

### Non-Functional Requirements
Use this format for each non-functional requirement:
```
**NFR-[ID]: [Category] - [Brief Title]**
- **Requirement**: Specific performance or quality criteria
- **Measurement**: How the requirement will be measured
- **Target Value**: Specific, numeric target
- **Rationale**: Why this requirement is important
- **Verification**: How compliance will be verified
```

### Constraints Documentation
Use this format for each constraint:
```
**Constraint-[ID]: [Type] - [Brief Description]**
- **Description**: Specific limitation or restriction
- **Impact**: How this constraint affects the project
- **Source**: Origin of the constraint (business, technical, regulatory)
- **Mitigation**: Strategies to work within or around the constraint
```

## Success Indicators

The skill is successful when:
- All stakeholders can understand the requirements regardless of technical background
- Requirements are clearly separated by type and priority
- Each requirement has measurable acceptance criteria
- The presentation facilitates productive discussion and decision-making
- Project scope and boundaries are unambiguously defined
- Implementation planning can proceed based on the documented requirements
